1 项目概述
1.1 项目背景
方壶美业当前采用“总部统一供货物料、加盟商开店经营”的模式扩张。门店前台事务，包括预约、排房、技师排班、收银与会员管理，已由门店店务系统承载，能够满足单店日常经营；但总部对加盟商、门店、物料与资金的管控仍主要依赖表格与线下沟通，随着加盟商与门店数量增长，暴露出三类结构性问题。
第一，组织与权限无法分层。总部、加盟商、门店之间缺少统一的组织模型与数据边界，加盟商的经营数据与供货数据混在同一批表格中流转，既无法保证加盟商只能看到自己的数据，也无法让总部一次性掌握全局。
第二，供货价格缺少统一口径。总部对不同合作等级的加盟商执行不同供货价，现有做法依赖人工查价、口头确认，价格版本多、追溯难，一旦等级调整或价格调整，历史单据与当期单据容易混淆。
第三，单据与库存无法追溯。总部发货、门店签收、门店库存三者之间没有形成闭环，既无法确认物料是否真正到店，也无法回答“这家门店当前有多少物料、本月从总部进了多少货、应付多少货款”。
本项目建设一套位于门店店务系统之上的供应管控中台，集中承载组织档案、分级定价、总部销货、门店入库、库存台账与对账导出，不改造门店现有的预约排房与收银流程，门店员工的操作习惯保持不变。

2 业务模型与组织架构
2.1 三级组织关系
系统采用三级组织模型：总部为顶层，向下辖两类实体，一类是直营门店，另一类是加盟商；加盟商再向下辖加盟门店。门店是最小业务单元，也是库存归属与单据收货的对象。每个门店有且只有一个上级：直营门店归属总部，加盟门店归属唯一的加盟商。该关系如图1所示。

图1 三级组织与供货关系
组织模型中不引入“区域”与“城市”等中间层级，避免早期过度设计。如果后续需要按大区管理，可在加盟商之上增加一层区域组织，届时只需在组织表中扩展父级指针，不影响已有的门店与单据数据。
2.2 直营门店与加盟门店的差异
两类门店在组织、定价、结算三个维度上的处理方式不同，必须在系统中显式区分，不能靠门店名称或备注推测。差异如表4所示。

2.3 加盟商等级体系
等级是分级供货定价的维度，采用可维护的字典表存储，不写死在代码中。每个等级包含等级编码、等级名称、排序号与状态。等级编码一经创建不可修改，因为它是定价记录的关联键；等级名称可以修改，不影响价格数据。
等级的典型取值为普通、白银、黄金、钻石四档，实际档位数量由业务方确定，建议不超过六档，档位过多会增加定价维护成本，也容易在报价时产生歧义。等级与物料价格的关系是一对多的组合关系，即同一物料对每一档等级各有一条价格记录。
2.4 核心业务规则
下列五条规则贯穿全系统的功能设计与技术实现，任何模块的实现都不得违反。规则在代码中表现为定价解析、单据快照、库存唯一约束与状态机约束，在数据库中表现为唯一索引与字段约束。

数据隔离采用行级过滤，不做独立库或独立 Schema。所有涉及门店与单据的业务表都携带归属字段，其中门店表携带 franchisee_id，单据与库存表携带 store_id。账号在登录后解析出数据范围，全系统统一使用三种范围取值。

需要特别说明的是，加盟商级过滤不能简单地“查询自己名下的门店再拼接”。正确做法是由拦截器在数据访问层统一追加条件，业务代码不参与条件拼接。这样即使某个开发人员漏写过滤条件，也不会造成越权，因为过滤发生在 SQL 生成阶段而非业务逻辑阶段。
3.3 权限校验落点
权限校验分为三层。第一层是认证，由统一鉴权组件校验令牌有效性并解析当前账号；第二层是功能权限，校验当前角色是否具备该接口的操作权限；第三层是数据权限，由数据权限拦截器在查询与更新语句上追加归属条件。三层均在后端完成。
前端只负责菜单与按钮的显隐，属于体验优化，不构成安全边界。任何依赖前端隐藏来实现的隔离都视为缺陷。越权请求在后端返回 403，并写入审计日志，记录请求账号、目标资源与发生时间，便于事后追查。
4 功能需求
本章按模块描述功能需求，每个模块给出字段定义、操作范围与业务校验。所有金额字段保留两位小数并按四舍五入计算，所有编码类字段一经生成不可修改。
4.1 加盟商等级管理
等级管理面向总部超级管理员，用于维护分级供货定价的维度。新增等级时校验编码唯一性，编码仅允许大写字母与下划线，长度不超过 16 位。停用等级后不可再分配给新加盟商，已绑定该等级的加盟商保持原等级，系统在加盟商列表中提示“等级已停用”。

4.3 门店管理
门店是最小业务单元，须显式标注类型。新增门店时按类型分支校验：类型为加盟门店时，所属加盟商必填且必须为正常状态的加盟商；类型为直营门店时，所属加盟商必须为空，若前端误传则后端拒绝。同一加盟商下的门店名称不可重复。

4.5 分级供货定价
分级定价是本系统的核心能力。定价记录由物料、加盟商等级与供货价三元组构成，同一物料对同一等级只允许一条记录。总部可按物料批量维护各等级价格，也可按等级批量维护各物料价格，两种入口写入同一张定价表。
带价逻辑按固定顺序解析，顺序不可颠倒。第一步判断收货门店类型，直营门店直接取物料的直营调拨价，流程结束；第二步对加盟门店取其所属加盟商的当前等级，在定价表中查询该物料与该等级的组合；第三步若查询命中则采用等级供货价，未命中则回退物料的基准供货价。每次解析同时返回价格来源标识，便于单据追溯与财务解释。

4.7 门店入库与库存台账
门店确认入库时，系统在一个事务内完成四件事：校验单据状态为待确认、逐条累加门店库存、写入出入库流水、将单据状态更新为已确认。四步必须全部成功，任一步失败整体回滚，不允许出现“库存加了但单据还是待确认”的中间态。
库存按门店与物料唯一，数据结构上表现为 (store_id, material_id) 的唯一索引，数值上表现为当前库存量。库存更新采用原子累加语句，即直接执行数量自增，不在应用层先查后改，避免并发下的丢失更新。同时以“单据号 + 门店”作为幂等键，防止门店重复点击造成重复入库。
库存预警以物料主数据的预警下限为阈值，门店库存低于阈值时在库存列表与数据大盘中标记。预警只是提示，不阻断业务，避免因阈值设置不合理导致门店无法正常入库。
4.8 对账与导出
对账数据来源于已确认的销货单，未确认与已取消单据不计入。系统提供三个口径：按加盟商汇总应付供货金额、按门店汇总进货金额、按物料汇总供货数量与金额。三个口径基于同一批单据，汇总结果应当能够互相校验。
导出格式为 Excel，包含汇总页与明细页两张工作表。汇总页给出筛选条件下的加盟商、门店、单据数量与总金额；明细页逐条列出单据号、门店、物料、数量、单价、金额与确认日期，供财务核对。导出为只读操作，不修改任何业务数据。
4.9 数据大盘
大盘分总部视图与加盟商视图两套，数据权限决定展示范围，同一套统计逻辑按数据范围裁剪。总部视图聚焦全局扩张与供货情况，加盟商视图聚焦自身门店的进货与待办。

4.10 系统管理与审计日志
系统管理覆盖账号、角色与审计。账号由总部统一创建，加盟商管理员与门店操作员的账号必须绑定加盟商或门店，未绑定归属数据的账号不允许创建，从源头避免“无归属账号”造成的权限漏洞。
审计日志记录敏感操作，包括加盟商新增与等级变更、物料与价格修改、销货单创建与取消、单据单价手工覆盖、账号启用与停用。每条日志包含操作人、操作时间、操作类型、变更前后值与请求来源 IP，支持按时间与操作类型检索并导出。

6 技术架构设计
架构设计遵循三条原则：优先保证数据隔离与单据可追溯，优先保证单人可维护，优先保证二期扩展不必重构。在这一约束下，系统采用前后端分离的模块化单体架构，不引入微服务与消息中间件，等业务量增长到需要拆分时再拆，避免早期为架构而架构。
6.1 总体架构
系统自上而下分为表现层、接入与安全层、业务应用层、基础设施层。表现层为管理后台，按角色渲染三套视图；接入与安全层承担认证、鉴权与数据权限注入；业务应用层按领域划分模块；基础设施层提供数据库、缓存、对象存储与定时任务。整体结构如图3所示。

6.3 后端分层与模块划分
后端采用四层结构：接口层（Controller）、应用层（Service）、领域层（Domain）、基础设施层（Mapper 与外部适配）。接口层只做参数校验与响应包装，不含业务判断；应用层编排业务流程与事务边界；领域层承载定价解析、金额计算、状态流转等核心规则；基础设施层负责数据访问与文件存储。

模块之间只允许上层依赖下层，同层模块之间通过应用层接口调用，不允许跨模块直接访问对方的 Mapper。这样在二期拆分服务时，可以按模块边界整体迁移，改动范围可控。
6.4 关键设计
6.4.1 定价解析
定价解析实现为无状态的纯函数：输入门店、加盟商、物料，输出价格与价格来源。不查缓存、不携带上下文，因此可以被单元测试完整覆盖，也可以在批量导入与预算测算中复用。解析结果写入单据明细，作为快照长期保留。
public PriceResult resolvePrice(Store store, Material material) {     if (store.getStoreType() == StoreType.DIRECT) {         return PriceResult.of(material.getDirectPrice(), PriceSource.DIRECT);     }     String levelCode = franchiseeService.currentLevel(store.getFranchiseeId());     BigDecimal levelPrice = priceRepository.find(material.getId(), levelCode);     if (levelPrice != null && levelPrice.compareTo(BigDecimal.ZERO) > 0) {         return PriceResult.of(levelPrice, PriceSource.LEVEL);     }     return PriceResult.of(material.getBaseSalePrice(), PriceSource.BASE); }

6.4.2 单据状态机
状态流转集中在状态机类中实现，Controller 与 Service 不得直接修改状态字段。状态机对外只暴露“确认”“撤回”“取消”三个方法，每个方法内部校验当前状态是否允许流转，不允许则由业务异常中断。数据库层用条件更新兜底，形成应用与数据库双重约束。
UPDATE sale_order    SET status = 'CONFIRMED', confirmed_at = now()  WHERE id = #{id} AND status = 'PENDING';

6.4.3 库存一致性
入库确认涉及单据状态与库存两张表，必须处于同一事务。库存更新使用自增语句而非先查后改，避免并发丢失更新；同时对幂等键建立唯一约束，使重复请求在数据库层被拦截。事务成功提交后，单据状态与库存数量同时可见，不存在中间态。
UPDATE store_stock    SET current_qty = current_qty + #{qty}, updated_at = now()  WHERE store_id = #{storeId} AND material_id = #{materialId};

若门店首次入库某物料，库存记录尚不存在，此时先执行插入并依赖唯一索引兜底：并发插入冲突时捕获唯一约束异常，转为自增更新重试一次。该处理避免应用层加锁，同时保证结果正确。
6.4.4 数据权限拦截
数据权限以注解标记接口，以拦截器改写 SQL。注解声明该接口适用的数据范围类型，拦截器在查询与更新执行前追加归属条件。加盟商级追加 franchisee_id 条件，门店级追加 store_id 条件，全局不追加。由于条件在 SQL 层拼接，业务代码无需感知，也不存在漏写风险。

6.5 安全设计
安全设计覆盖认证、授权、数据、传输与依赖五个方面。认证采用令牌机制，令牌有效期 8 小时，支持主动失效；授权同时校验角色与数据范围；数据层面敏感字段（如联系电话）在非必要场景脱敏输出；传输全站启用 HTTPS；依赖层面在构建阶段执行漏洞扫描，高危漏洞阻断发布。
数据库不暴露公网端口，仅允许应用服务器内网访问。所有 SQL 通过参数化执行，禁止字符串拼接。文件访问采用带时效签名地址，有效期 30 分钟，避免合约与凭证被长期外链传播。密码采用强哈希算法存储，登录失败次数超限后短期锁定。

7 数据库设计
数据库设计以可追溯与可校验为核心。所有业务表包含创建时间与更新时间，所有涉及归属的表包含门店或加盟商标识，金额字段统一使用 numeric 类型，编码字段建立唯一索引。
7.1 设计原则
第一，归属字段不下沉到明细。单据明细通过单据主表关联门店，避免明细与主表的归属字段不一致。第二，快照字段与源字段并存。门店类型、加盟商、单价在单据中保存快照，源数据变化不影响历史。第三，唯一索引承担并发约束。库存、定价、单号均以唯一索引兜底，应用层的校验不作为唯一保障。

8 接口设计
接口遵循统一的路径前缀、统一的响应结构与统一的错误码，前端据此实现拦截器与错误提示，减少逐接口适配。
8.1 接口规范
所有接口以 /api/v1 为前缀，采用 RESTful 风格语义。请求头携带 Bearer 令牌，令牌由登录接口下发。响应结构统一为四字段：业务码、提示信息、数据体与请求追踪号。业务码 200 表示成功，401 表示未登录或令牌失效，403 表示权限不足或越权，400 表示参数校验失败，500 表示服务端异常。
{   "code": 200,   "msg": "ok",   "data": { },   "requestId": "b1c2d3e4-..." }

分页接口统一使用 pageNum 与 pageSize 参数，返回 total 与 records。导出类接口不返回 JSON，直接返回文件流，文件名采用“业务名+日期”格式，便于财务归档。

10.2 环境与配置
配置分为三类：数据库与缓存连接、安全参数（令牌有效期、密码策略、文件签名有效期）、业务参数（预警阈值、导出条数上限）。前两类通过环境变量注入，业务参数在管理后台维护，避免每次调整参数都要重启服务。
10.3 备份与恢复
数据库每日凌晨执行全量备份，保留最近七天的备份文件，每周另存一份到异地。对象存储中的附件按周增量同步。恢复流程在项目交付前至少演练一次，并记录恢复耗时，避免真正需要恢复时才发现脚本不可用。

11.3 验收标准
验收以可复现的操作路径为准，不以“功能已开发”作为通过条件。下列六条全部满足方可判定一期交付完成。
	•	加盟商账号登录后仅能看到本加盟商及其名下门店的数据，尝试访问其他加盟商单据返回 403
	•	同一物料对钻石、黄金、普通三档等级带出不同供货价，缺失等级价时回退基准价并标注价格来源
	•	直营门店单据取直营调拨价，与加盟门店价格互不影响
	•	门店确认入库后库存与流水同步更新，重复提交不产生重复入库
	•	取消单据保留全部明细，历史单据单价在调价后保持不变
	•	按加盟商、门店、物料三个口径汇总的金额互相一致，导出文件与页面数据一致
12 风险与约束
